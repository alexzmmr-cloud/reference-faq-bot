# Spec — Reference FAQ Bot (v2)

## Назначение
- Пользователь мгновенно получает ответ на частый вопрос об учебном сервисе через Telegram-бота
- Пользователь может уточнить вопрос свободным текстом, а не только кнопками
- Пользователь, которому бот не смог помочь, может оставить сообщение для оператора и получить подтверждение, что оно принято
- Владелец/админ бота узнаёт о новом обращении к оператору сразу, не заглядывая в БД вручную (v2)

## Пользовательский сценарий
- Пользователь отправляет `/start`
- Бот показывает приветствие и inline-кнопки: «О курсе», «Стоимость», «Формат обучения», «Связаться с оператором»
- Пользователь нажимает FAQ-кнопку
- Бот показывает готовый ответ из `faq.json` и повторно показывает те же inline-кнопки
- Пользователь вместо кнопки пишет свободный текст
- Бот ищет совпадение по `keywords` (вхождение подстроки, без учёта регистра) и отвечает найденным `answer`, повторно показывая кнопки
- Пользователь пишет текст, для которого совпадений нет
- Бот не ломает сценарий: отвечает, что не понял, и предлагает выбрать кнопку или обратиться к оператору
- Пользователь нажимает «Связаться с оператором»
- Бот просит прислать одно сообщение
- Пользователь присылает текстовое сообщение
- Бот сохраняет его в SQLite (`operator_requests`), отправляет уведомление владельцу/админу (v2) и присылает пользователю понятное подтверждение, что обращение принято
- Пользователь во флоу «Связаться с оператором» присылает не текст (фото/стикер/войс)
- Бот не сохраняет это как обращение и просит прислать именно текстовое сообщение

## Сущность: faq item (faq.json)
- `id` — string, стабильный идентификатор раздела, используется в `callback_data` в формате `faq:<id>`
- `button` — string, текст inline-кнопки
- `keywords` — array of string, слова/фразы для поиска по вхождению подстроки
- `answer` — string, готовый ответ пользователю

## Разрешённые значения `id` (faq.json, v1)
- `about`
- `price`
- `format`

## Сущность: operator_requests (SQLite)
- `id` — integer, автоинкрементный PK
- `telegram_user_id` — integer, Telegram id пользователя
- `username` — string, nullable (может отсутствовать у пользователя)
- `message_text` — string, текст обращения
- `created_at` — string, ISO-8601 UTC, время создания записи

## Уведомление владельца/админа (v2)
- Переменные окружения `OWNER_CHAT_ID` и `ADMIN_CHAT_ID` — Telegram chat_id, читаются из `.env`
- В текущем тестовом режиме обе переменные содержат один и тот же chat_id
- После успешного сохранения обращения в `operator_requests` бот отправляет уведомление на каждый уникальный chat_id из `OWNER_CHAT_ID`/`ADMIN_CHAT_ID`
- Текст уведомления: текст обращения + `telegram_user_id` + `username` (или пометка «без username»)
- Уведомление — best-effort: сбой отправки (невалидный chat_id, owner не запускал бота, недоступность Telegram API) не должен ломать ответ пользователю — обращение уже сохранено в БД, это главная гарантия; ошибка отправки логируется, но не всплывает пользователю
- Если ни `OWNER_CHAT_ID`, ни `ADMIN_CHAT_ID` не заданы или оба не парсятся как integer — это ошибка конфигурации, обнаруживается при старте бота (`RuntimeError`), а не во время обработки сообщения пользователя

## Требования к результату
- `/start` показывает приветствие и 4 inline-кнопки: 3 FAQ-кнопки из `faq.json` + «Связаться с оператором»
- Все FAQ-ответы читаются из `faq.json`, не хардкодятся в коде/промпте
- После любого FAQ-ответа (по кнопке или по keyword) повторно показываются те же inline-кнопки
- Поиск по свободному тексту — вхождение подстроки любого `keyword` в текст пользователя (регистр игнорируется)
- Нераспознанный текст не роняет бота — короткое сообщение «не понял» + предложение выбрать кнопку/оператора
- Флоу «оператор» принимает только текстовые сообщения; нетекстовые — просит прислать текст, не сохраняет и не завершает флоу
- Успешная запись в `operator_requests` подтверждается пользователю явным сообщением независимо от результата отправки owner/admin-уведомления
- После сохранения обращения бот пытается уведомить всех получателей из `OWNER_CHAT_ID`/`ADMIN_CHAT_ID`; сбой уведомления логируется и не блокирует ответ пользователю
- `BOT_TOKEN` читается из `.env`, реальный токен не появляется в коде, логах, коммитах и в ответах ассистента
- `.env.example` содержит только заглушки (`BOT_TOKEN`, `OWNER_CHAT_ID`, `ADMIN_CHAT_ID`)
- Форму `faq.json` и таблицы `operator_requests` менять нельзя без обновления этого spec.md
- Новые FAQ-разделы/поля сверх зафиксированного списка не добавлять без отдельной задачи

## Данные
- `faq.json` — источник данных для FAQ-кнопок и текстового поиска, лежит в корне проекта
- SQLite-файл базы данных — `requests.sqlite3`, создаётся локально при первом запуске (схема — по разделу «Сущность: operator_requests»)
- Смена формы `faq.json` или схемы `operator_requests` требует одновременного обновления этого spec.md

## Backend
- Python, `aiogram==3.28.2`, long polling (без вебхуков)
- `python-dotenv==1.2.2` — чтение `BOT_TOKEN` из `.env`
- `sqlite3` (стандартная библиотека) — хранение `operator_requests`
- `logging` (стандартная библиотека) — логирование событий бота
- `json` (стандартная библиотека) — чтение `faq.json`

## Явно не входит в scope
- Frontend/веб-интерфейс — только Telegram-бот
- Разные chat_id для owner и admin (роли не разделены в v2, оба читаются из отдельных переменных, но в тестовом режиме указывают на один chat_id)
- Повторные попытки (retry) при сбое отправки уведомления — только одна попытка + лог ошибки
- Редактирование `faq.json` через бота или админку
- Многоязычность
- VPS/деплой на сервер, вебхуки, production-эксплуатация
- API ИИ, CRM, приём оплаты
- Автотесты — проверка только через smoke-check `/start` в Telegram

## Допущения
- `username` в `operator_requests` может быть NULL, если у пользователя не задан username в Telegram
- Один флоу «оператор» = одно сообщение; после сохранения флоу завершается, повторных сообщений в рамках того же флоу не ожидается
- Точные тексты приветствия и ответов FAQ формулирует исполнитель на этапе реализации в рамках заданных 3 тем (о курсе / стоимость / формат)
